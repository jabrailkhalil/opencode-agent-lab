# Анализ требований и неоднозначностей

## Полные критерии спецификации (SPEC)

### Функциональные требования

1. **Управление задачами**:
   - Создание, просмотр, редактирование и удаление задач.
   - Поля задачи: название (1-140 символов после trim), описание (до 1000 символов), ответственный (один из 4 сотрудников или null), оценка в часах (0.5-168 с шагом 0.5), статус (todo/doing/done), неделя (понедельник в формате YYYY-MM-DD).

2. **Представления задач**:
   - Доска Kanban с тремя колонками (todo/doing/done) с возможностью drag-and-drop.
   - Представление задач по сотрудникам.
   - Переключение между представлениями.

3. **Поиск и фильтрация**:
   - Поиск по названию и описанию задач.
   - Фильтр по ответственному.
   - Поиск не влияет на расчет недельной нагрузки.

4. **Недельное планирование**:
   - Навигация между неделями (предыдущая/следующая).
   - Начальная неделя: 2026-09-28.
   - Задачи и доступность по неделям независимы.

5. **Управление доступностью сотрудников**:
   - 4 сотрудника: Анна, Дмитрий, Мария, Илья.
   - Настройка недельной доступности от 0 до 168 часов.
   - Загрузка: активные часы / доступные часы (округленный процент и перегрузка в часах).
   - Прогресс: выполненные часы / все назначенные часы текущей недели.

6. **Планирование нагрузки**:
   - Предложение распределения активных задач с предпросмотром.
   - Возможность отмены или применения предложенного плана.
   - Нельзя назначать сверх доступности.
   - Не помещающиеся задачи остаются без ответственного.
   - Выполненные задачи, задачи других недель, общее количество задач и часов сохраняются.

7. **Хранение данных**:
   - Использование localStorage для сохранения изменений.
   - Обработка поврежденных данных без падения приложения.
   - Возможность восстановления учебного примера после подтверждения.

8. **Валидация формы**:
   - Название: 1-140 символов после trim.
   - Описание: до 1000 символов.
   - Оценка: 0.5-168 с шагом 0.5.
   - Ответственный: существующий сотрудник или null.
   - Статус: допустимый статус.
   - Неделя: дата должна быть понедельником.
   - Ошибки отображаются в открытой форме, значения не сбрасываются.

9. **UI/UX требования**:
   - Полный адаптивный дизайн для ширины экранов 390, 768, 1100, 1280 px.
   - Никакого горизонтального переполнения.
   - Загрузка и прогресс каждого сотрудника всегда видны.
   - Подписанные формы, управление клавиатурой.
   - Единый стиль Tabler.

### Технические требования

1. **Структура проекта**:
   - Создать файлы: dist/index.html, dist/styles.css, dist/app.js, dist/domain.js.
   - Использовать локальный CSS Tabler из dist/vendor/tabler/.
   - Не использовать npm install, сборщики, backend, облачную публикацию или вход пользователей.

2. **Domain API**:
   - Экспортировать из dist/domain.js: DEMO_WEEK='2026-09-28', seedState(), monday(date), loadFor(state, employeeId, week), validateTask(task, employees), proposePlan(state, week), applyPlan(state, plan), isValidState(state).

3. **Тестирование**:
   - Прохождение всех 9 заранее зафиксированных приёмочных проверок из tests/acceptance.test.mjs.
   - Добавление атрибутов data-testid для UI элементов согласно контракту.
   - Запуск node --test tests/*.test.mjs и node scripts/verify.mjs.

## Замеченные неоднозначности и вопросы

1. **Алгоритм распределения задач**:
   - В пункте 8 SPEC упоминается, что алгоритм распределения можно выбрать самостоятельно. Необходимо уточнить критерии "справедливого" распределения (например, равномерное распределение по доступности, приоритеты задач и т.д.).

2. **Обработка перегрузки при планировании**:
   - Не до конца ясно, как именно обрабатывать перегрузку: переставлять задачи на следующую неделю, уведомлять пользователя, или просто оставлять без назначения?

3. **Формат даты недели**:
   - В QA-07 упоминается "следующая неделя пустая", но не уточняется, как именно определяется "следующая неделя". Это календарная неделя или неделя с шагом 7 дней?

4. **Поведение при повреждении данных**:
   - В пункте 9 SPEC говорится о восстановлении учебного примера после подтверждения. Необходимо уточнить, когда именно показывается диалог восстановления: при любом повреждении или только при полной нечитаемости данных?

5. **Точное поведение поиска**:
   - В пункте 4 SPEC уточняется, что поиск не пересчитывает нагрузку по найденным задачам. Но неясно, влияет ли фильтр по ответственному на отображение нагрузки?

6. **Визуализация состояния задач**:
   - В DESIGN-REFERENCE.md говорится о необходимости акцентировать внимание на статусе задачи, но не уточняется, как именно это должно быть реализовано в UI (цвета, иконки и т.д.).

7. **Поведение drag-and-drop**:
   - Не до конца ясно, как именно должен работать drag-and-drop между представлениями (канбан и по сотрудникам). Нужно ли сохранять промежуточное состояние при перетаскивании?

8. **Сценарии обработки ошибок**:
   - Не уточнены сценарии, при которых могут возникнуть ошибки при сохранении в localStorage (например, превышение лимита хранилища).
