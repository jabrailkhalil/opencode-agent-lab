## ADDED Requirements

### Requirement: Расчёт загрузки сотрудника
`loadFor(state, employeeId, week)` MUST считать по задачам сотрудника выбранной недели. Активные — todo и doing; done SHALL NOT занимать доступность. Результат MUST содержать `{tasks, active, hours, capacity, totalHours, doneHours, overload, percent, progress}`. `capacity` MUST браться из `capacities[week]` при наличии (включая 0), иначе из `capacity`. `percent` = `Math.round(hours / capacity * 100)`, `overload` = `max(0, hours - capacity)`; при capacity=0 `percent` MUST быть null.

#### Scenario: Перегрузка Анны на seed
- **WHEN** считается загрузка `anna` за 2026-09-28
- **THEN** hours=32, capacity=24, percent=133, overload=8

#### Scenario: Выполненные не занимают доступность
- **WHEN** у Ильи 12 ч (todo) и 4 ч (done), доступность 24
- **THEN** hours=12, doneHours=4, totalHours=16, percent=50, overload=0

#### Scenario: Нулевая доступность с активными задачами
- **WHEN** capacity недели равна 0 и есть активные часы (или их нет)
- **THEN** percent=null; overload равен активным часам (0 без них); нет NaN/Infinity; UI MUST показать «нет доступности», а не «null»/«NaN%»

#### Scenario: Недельная доступность переопределяет базовую
- **WHEN** `capacities['2026-10-05']=40` у Анны
- **THEN** для 10-05 capacity=40, для 09-28 остаётся 24

### Requirement: Расчёт прогресса
Прогресс SHALL равняться `Math.round(doneHours / totalHours * 100)`, где totalHours — все назначенные сотруднику часы недели (todo+doing+done). При totalHours=0 прогресс MUST быть 0 без NaN/Infinity. Прогресс MUST не зависеть от доступности, поиска и фильтра.

#### Scenario: Прогресс на seed
- **WHEN** считается прогресс за 2026-09-28
- **THEN** Мария 43% (6/14), Илья 25% (4/16), Анна 0%, Дмитрий 0%

#### Scenario: Нет назначенных часов или нулевая доступность
- **WHEN** у сотрудника нет задач недели; отдельно: capacity=0 при наличии выполненных часов
- **THEN** progress=0 без NaN; во втором случае percent=null, а progress остаётся числом по часам

### Requirement: Начальные данные
`seedState()` MUST возвращать независимую глубокую копию `docs/seed-state.json`: 9 задач, 80 ч, 7 активных задач / 70 активных часов, nextId=110, неделя всех задач DEMO_WEEK. Мутация копии SHALL NOT влиять на следующий вызов.

#### Scenario: Независимые копии seed
- **WHEN** у результата `seedState()` изменены задача и nextId, затем вызван `seedState()` повторно
- **THEN** новая копия содержит 9 задач, 80 ч и nextId=110

### Requirement: Недели
`monday(date)` MUST возвращать понедельник YYYY-MM-DD независимо от часового пояса (UTC-арифметика). prev/next SHALL сдвигать неделю на 7 дней, `current-week` MUST вернуть DEMO_WEEK. Задачи и доступность разных недель MUST быть независимы.

#### Scenario: Понедельник и независимость недель
- **WHEN** `monday('2026-10-04')`; отдельно next-week с 09-28, затем на 09-28 доступность Анны меняется на 40
- **THEN** '2026-09-28'; на 10-05 задачи 09-28 не видны, capacity Анны на 10-05 прежний

### Requirement: Валидация задачи
`validateTask(task, employees)` MUST вернуть нормализованную копию, не мутируя вход, либо бросить Error с русским сообщением. Правила: название после trim 1–140; описание после trim до 1000; hours — число 0,5–168 с шагом 0,5 (числовая строка из формы допустима; NaN, пусто, 0.3, 168.5 отклоняются); assignee — id существующего сотрудника или null; status ∈ {todo, doing, done}; week — реальная дата YYYY-MM-DD, являющаяся понедельником.

#### Scenario: Нормализация и пустое название
- **WHEN** название '  Тест  ' и описание ' текст '; отдельно название '   '
- **THEN** копия содержит 'Тест' и 'текст', вход не изменён; для '   ' выбрасывается Error

#### Scenario: Границы
- **WHEN** название 140/141 симв., описание 1000/1001, hours 0.5/0.4/168/168.5/1.25
- **THEN** допустимы 140, 1000, 0.5, 168; остальные отклоняются

#### Scenario: Некорректные связи
- **WHEN** assignee='ghost', status='blocked' или week='2026-09-29'
- **THEN** выбрасывается Error; assignee=null допустим

### Requirement: Форма задачи
UI SHALL давать форму `task-form` для создания и редактирования с подписанными полями (`label`/`for`). При ошибке валидации форма MUST оставаться открытой, `task-error` MUST показать причину, введённые значения SHALL NOT сбрасываться. Пустое название MUST отклоняться прикладной trim-валидацией независимо от HTML `required`. По умолчанию: выбранная неделя, статус todo, «Без ответственного». `task-cancel` SHALL закрывать форму без изменений.

#### Scenario: Ошибка не сбрасывает ввод
- **WHEN** название '   ', описание 'abc', hours 5, нажат task-save
- **THEN** форма открыта, task-error виден, 'abc' и 5 сохранены, задача не создана

#### Scenario: Создание
- **WHEN** введены корректные поля и нажат task-save
- **THEN** задача получает id TASK-110, nextId=111, форма закрыта, видна `task-TASK-110`

#### Scenario: Редактирование и удаление
- **WHEN** edit-TASK-101 → статус done → сохранить; затем delete-TASK-109 с подтверждением
- **THEN** форма была предзаполнена, TASK-101 в «Готово», прогресс Анны пересчитан; TASK-109 исчезла из обоих представлений и из localStorage

### Requirement: Доска и представление по сотрудникам
Доска `board` SHALL иметь колонки `column-todo/doing/done` («Новая», «В работе», «Готово»). Перетаскивание в колонку MUST менять статус, смена через форму MUST давать тот же результат. `employees-view` MUST группировать те же задачи по сотрудникам и «Без ответственного». `view-board`/`view-employees` MUST сохранять данные, поиск и фильтр.

#### Scenario: Drag-and-drop
- **WHEN** TASK-102 перетащена в `column-done`
- **THEN** статус done, у Анны hours=16, progress=50%

#### Scenario: Переключение представлений
- **WHEN** выбран view-employees, затем view-board при активном фильтре
- **THEN** задачи и значения те же, фильтр сохранён

### Requirement: Поиск и фильтр
`search` SHALL отбирать задачи по вхождению без учёта регистра в название или описание; `filter-assignee` — по id (пусто = все). Они MUST влиять только на список задач; `load-*`/`progress-*` SHALL считаться по всем задачам недели.

#### Scenario: Поиск не меняет нагрузку
- **WHEN** в search введено «витрин»
- **THEN** видна только TASK-102, load-anna остаётся 32/24 (133%)

### Requirement: Недельная доступность
Для каждого сотрудника SHALL быть поле `capacity-<id>` со значением 0–168 (шаг 0,5), сохранение на change/blur. 0 MUST быть допустимым и не откатываться к базовому. Недопустимое значение (<0, >168, не число) MUST отклоняться с сообщением, прежнее значение восстанавливается.

#### Scenario: Нулевое и недопустимое значения
- **WHEN** в capacity-anna введено 0; отдельно 169 или -1
- **THEN** 0 сохранено, load-anna показывает «нет доступности» и перегрузку 32 ч; 169/-1 не сохраняются, показана ошибка

### Requirement: Отображение нагрузки и прогресса
Карточка `employee-<id>` MUST содержать подписанные `load-<id>` («активные / доступные ч», процент, «+N ч» при перегрузке) и `progress-<id>` (процент и часы). Перегрузка SHALL выделяться не только цветом. Нулевой знаменатель MUST показываться текстом.

#### Scenario: Значения seed
- **WHEN** открыта неделя 09-28
- **THEN** Анна 32/24, 133%, +8 ч; прогресс Марии 43%, Ильи 25%

### Requirement: Предложение распределения
`proposePlan(state, week)` MUST вернуть `{assignments:[{taskId,assignee}], unassignedHours}` без мутации state. Рассматриваются только активные задачи недели, каждая ровно один раз; done и чужие недели SHALL NOT затрагиваться. Сумма часов сотрудника MUST быть ≤ его доступности недели (при 0 — ничего). Не помещающаяся целиком задача MUST получить assignee=null, её часы входят в `unassignedHours`.

#### Scenario: Seed: 70 активных часов, доступность 104
- **WHEN** предлагается план на seed
- **THEN** ни у кого нет перегрузки, все 7 активных задач (включая TASK-109) получают ответственного, unassignedHours=0

#### Scenario: Дефицит доступности
- **WHEN** на seed доступность недели: Дмитрий 16, остальные 0 (суммарно 16, активных 70 ч); отдельно задача 16 ч при максимальной доступности сотрудника 8 ч
- **THEN** unassignedHours=54 (16 ч назначены Дмитрию целиком одной задачей), равно часам задач с null, перегрузки нет; задача 16 ч остаётся без ответственного; если у всех доступность 0 — unassignedHours=70

### Requirement: Применение плана
`applyPlan(state, plan)` MUST вернуть новое состояние (вход не мутируется), меняя только assignee активных задач; число задач, id и общая сумма часов сохраняются.

#### Scenario: Сохранение инвариантов
- **WHEN** план применён
- **THEN** done-задачи и чужие недели не изменены, число задач и сумма часов прежние

### Requirement: UI предпросмотра плана
`propose-plan` SHALL открыть `plan-preview` со списком «задача: было → станет» и итогом unassignedHours, не меняя данные и localStorage. `plan-apply` MUST применить и сохранить план; `plan-cancel` MUST закрыть предпросмотр без изменений. Автоматическое применение SHALL NOT допускаться.

#### Scenario: Предпросмотр, отмена, применение
- **WHEN** нажат propose-plan, затем plan-cancel; потом снова propose-plan и plan-apply
- **THEN** после предпросмотра и отмены данные и load-* прежние; после применения назначения обновлены, load-* пересчитаны, предпросмотр закрыт

### Requirement: Хранение
Состояние SHALL сохраняться в localStorage после каждого изменения и загружаться при старте. `isValidState(state)` MUST принять корректный seed и отклонять дубли id, неверные поля сотрудников/задач, неизвестного ответственного и nextId < 110. Повреждённый JSON или невалидная структура MUST NOT ронять приложение: загружается seed, показывается уведомление. `reset-demo` MUST восстанавливать seed только после подтверждения.

#### Scenario: Перезагрузка
- **WHEN** создана задача, изменена доступность, страница перезагружена
- **THEN** задача и доступность на месте

#### Scenario: Повреждённые данные
- **WHEN** в localStorage '{bad json' или состояние с дублями id
- **THEN** `app` виден, загружен seed, есть уведомление

#### Scenario: Сброс
- **WHEN** нажат reset-demo, подтверждение отклонено, затем принято
- **THEN** при отказе данные не изменены; при подтверждении восстановлен seed

### Requirement: Адаптивность и доступность
Интерфейс MUST использовать локальный Tabler без внешних ресурсов и отображаться при 390, 768, 1100 и 1280 px без горизонтального переполнения; нагрузка и прогресс каждого сотрудника SHALL быть доступны на всех ширинах. Все поля MUST иметь подписи, действия — достижимы с клавиатуры с видимым фокусом; drag-and-drop MUST иметь альтернативу через форму.

#### Scenario: Узкий экран
- **WHEN** ширина 390 px
- **THEN** scrollWidth ≤ clientWidth, load-*/progress-* видимы
