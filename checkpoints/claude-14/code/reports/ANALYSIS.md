# ANALYSIS: «Поток» — трекер задач и недельный планировщик

Источники: docs/SPEC.md, docs/DOMAIN-CONTRACT.md, docs/DESIGN-REFERENCE.md, docs/QA-CHECKLIST.md, docs/seed-state.json. Дополнительно прочитан tests/acceptance.test.mjs (на него ссылается контракт). scripts/verify.mjs не читался: менять его запрещено, а его содержимое не входит в docs.

Состояние рабочей папки на момент анализа: есть dist/vendor/tabler/ (CSS, LICENSE, source.json), tests/acceptance.test.mjs, scripts/{verify,serve,browser-mcp}.mjs. Файлов dist/index.html, styles.css, app.js, domain.js нет.

## 1. Артефакты и ограничения

- Создать: dist/index.html, dist/styles.css, dist/app.js, dist/domain.js. Это чистый статический фронтенд.
- Нельзя: код предыдущего приложения, npm install, сборщик, backend, облако, авторизация.
- Сервис доступен на http://127.0.0.1:4190/ (статический сервер уже запущен).
- Стиль: локальный Tabler (dist/vendor/tabler/tabler.min.css). Акцент #206bc4, текст #182433, фон #f6f7f9, границы #e6e8ec, ошибка #d63939, завершение #2fb344.
- Нельзя менять tests/acceptance.test.mjs и scripts/verify.mjs. Тестировщик может добавлять только tests/agent-*.test.mjs.
- Результаты проверок сохраняются в reports/ (в том числе reports/host-verification.json, который пишет verify.mjs) и в скриншотах.
- «Готово» означает, что реализован весь объём и выполнены браузерные проверки. Частичный прототип нельзя объявлять завершённым.

| F6 | Доступность каждого из 4 сотрудников на выбранную неделю: число 0–168, сохраняется на change/blur. В нагрузку идут только незавершённые задачи недели. |
| F7 | Загрузка = активные часы / доступные часы, процент Math.round, перегрузка в часах. Прогресс = выполненные часы / все назначенные часы недели. Нулевой знаменатель не даёт NaN/Infinity. |

| F11 | Адаптивность на 390/768/1100/1280 px без горизонтального переполнения. Нагрузка и прогресс всех четырёх сотрудников видны на каждой ширине. Подписанные поля форм, управление с клавиатуры, единый стиль Tabler. |

### 2.3 Контракт domain.js (экспорт)

Экспортировать: `DEMO_WEEK='2026-09-28'`, `seedState()`, `monday(date)`, `loadFor(state, employeeId, week)`, `validateTask(task, employees)`, `proposePlan(state, week)`, `applyPlan(state, plan)`, `isValidState(state)`.

- seedState() возвращает независимую копию seed. Мутация результата не влияет на следующий вызов.
- monday() возвращает YYYY-MM-DD понедельника недели даты и не зависит от часового пояса. Нужна арифметика по UTC или по компонентам даты, без локального `new Date(str)` с локальными геттерами. Проверки: 2026-10-01 → 2026-09-28, 2026-10-04 → 2026-09-28, 2026-10-05 → 2026-10-05.
- loadFor() возвращает `{tasks, active, hours, capacity, totalHours, doneHours, overload, percent, progress}`.
  - capacity = `capacities[week]`, если задан, иначе `capacity`.
  - percent = null при нулевой доступности; progress = 0 при totalHours = 0. Округление Math.round.
  - По тестам: `tasks` включает и выполненные задачи недели (в тесте 2 их 2 при одной done). `hours` — только активные часы.
- validateTask() возвращает нормализованную копию или бросает Error. Вход не мутируется. Название и описание trim-ятся.
  - Отклонять hours: -1, 0, 0.7, 169, NaN, Infinity.
  - Принимать hours 0.5.
  - Отклонять пустое/пробельное название и несуществующего ответственного.
- proposePlan() возвращает `{assignments:[{taskId,assignee}], unassignedHours}` и не мутирует state.
- applyPlan() возвращает новое состояние, не мутируя старое.
- isValidState() принимает seed после JSON-сериализации. Отклоняет дубли ID, неверные поля, nextId < 110 и nextId = -1.

## 3. Замеченные неоднозначности и риски

1. **Задачи без ответственного в расчётах.** В загрузку сотрудников они не входят. Но «7 активных задач / 70 активных часов» и `unassignedHours` их учитывают. Предположение: 70 ч включает TASK-109 (4 ч), а сумма активных часов четырёх сотрудников равна 66. Нужно показывать «Без ответственного» отдельно и не терять эти часы в итогах недели.
2. **Алгоритм распределения должен быть оптимальным, а не жадным.** Тест 3 требует `unassignedHours === 54` при единственной доступности 16 ч у Дмитрия. Активные задачи: 16, 16, 8, 6, 8, 12, 4. Жадный проход «по порядку» (8+6=14) даёт 56 и тест не проходит. Нужно заполнять доступность максимально (сортировка по убыванию, подбор подмножества или knapsack). Тест фиксирует только этот случай; для других результат не определён.
3. **Смысл доступности в плане.** Остаток доступности считать с учётом уже выполненных задач нельзя: они не занимают доступность. Не определено, сохранять ли существующие назначения активных задач (минимизация перемещений) или переназначать все. Тест 4 требует только нулевую перегрузку и отсутствие неназначенных. Пересчёт с нуля допустим, но QA-10 требует лишь «без перегрузки».
4. **Остаются ли «не помещающиеся» задачи, у которых был ответственный, без него.** Да: SPEC п.8 «остаются без ответственного», тест 3 требует нулевой перегрузки у всех. Значит applyPlan для такой задачи ставит `assignee: null`, даже если раньше назначение было. Контракт говорит об «ответственном по предложению», assignments содержит `assignee: null` для таких задач.
5. **Что входит в `plan.assignments`.** Все активные задачи недели или только изменённые? Неясно. Безопаснее включать все активные задачи недели, `assignee` может быть null.
6. **Чужие недели.** `proposePlan(state, week)` и UI работают только с задачами недели `week`. Другие недели не трогаются (тест 5).
7. **Содержимое `loadFor.tasks`.** Все задачи сотрудника на неделе, включая done (по тесту 2). Поле `active` — вероятно, число или массив активных задач; тип в контракте не указан. Тесты его не проверяют. Нужно выбрать и описать в коде.
8. **`percent` и `overload` при нулевой доступности.** percent = null (UI показывает «—» или «нет доступности»), overload = активные часы (32). При 0 активных часов и 0 доступности overload = 0.
9. **Округление.** Math.round для percent и progress (43 = 6/14, 25 = 4/16, 133 = 32/24). Часы выводить без артефактов float (шаг 0,5, значения вроде 0,5 нужно отображать корректно). Округление перегрузки не требуется (шаг 0,5).
10. **Прогресс и неназначенные задачи.** Прогресс сотрудника считается по его задачам недели (done / все). Для общего недельного прогресса знаменатель не определён: включать ли неназначенные? Предложение: показывать в сводке, заранее оговорив формулу (done / все часы недели, включая неназначенные).
11. **Поиск и фильтр против нагрузки.** SPEC п.4: поиск не пересчитывает нагрузку. Нагрузка и прогресс идут по всем задачам недели независимо от поиска и фильтра. Фильтр по ответственному — тоже только отображение (формально сказано только про поиск; применить то же правило к фильтру).
12. **Регистр и нормализация поиска.** Регистронезависимый поиск по подстроке в названии и описании; trim запроса. «витрину» должно находить TASK-102 («Подключить витрину метрик»). Не указано, учитывать ли ё/е и словоформы. Достаточно подстроки.
13. **Форма и неделя.** Поле `task-week` — input; тип не указан (date или text). Дата должна быть понедельником: отклонять или приводить через monday()? SPEC п.10 говорит «дата недели — понедельник», значит валидатор отклоняет не-понедельник. Приведение в UI допустимо только явно. Новая задача по умолчанию получает текущую выбранную неделю.
14. **Ограничение шага 0,5.** Проверять кратность 0,5 без ошибок float (hours*2 — целое). Строка и пустое значение — ошибка. Обработка NaN/Infinity — отклонять, а не падать.
15. **Типы входа в validateTask.** Не указано, принимать ли hours строкой («2»). UI передаёт число, поэтому в domain лучше требовать конечное число или явно приводить строку в UI. Приведение внутри validateTask может нарушить будущие проверки на «строку = ошибка».
16. **Идентификаторы задач.** Формат TASK-N, nextId = 110. isValidState отклоняет nextId < 110. Неясно, должен ли nextId быть строго больше максимального числового ID (в тесте 5 есть TASK-999 при nextId 110, но проверяется только loadFor/applyPlan, не isValidState). Для безопасности isValidState проверяет именно `nextId >= 110` и целое число. При создании задачи брать max(nextId, max id + 1).
17. **Проверка структуры в isValidState.** Список обязательных полей задачи и сотрудника, допустимых недель и значений capacity (0–168) контракт задаёт только в общих словах («неправильные поля»). Реализация должна быть строгой, но принимать seed после JSON.parse (`capacities` как объект, `assignee: null`). Не отклонять seed по «лишним» полям (initials, role, color).
18. **Удаление и ссылки.** У сотрудников нет CRUD, поэтому ссылок на удалённых сотрудников быть не должно. isValidState отклоняет задачи с несуществующим assignee.
19. **Повреждённый localStorage.** Нужны: ключ хранилища (не задан), поведение при невалидном JSON и при валидном JSON с неверной структурой. Предложение: молча откатиться к seed и показать неблокирующее уведомление. Не затирать повреждённые данные до явного действия пользователя — решение остаётся за разработчиком. Нужно также обработать недоступный localStorage (try/catch).
20. **Что сохранять в localStorage.** Состояние версии 1 (`version`, employees, tasks, nextId). Выбранная неделя, поиск, фильтр, представление не обязательны. Перезагрузка в QA-04 требует только сохранения задач; сохранение недели после перезагрузки в SPEC не требуется.
21. **Подтверждение восстановления примера.** Используется модальное окно или `confirm()`. Контроллер «умеет нажать подтверждение», но способ не определён. Нативный `confirm()` рискован для автоматизации. Предпочтительнее собственная модальная панель. Для удаления подтверждение в SPEC не требуется (QA-05: «удаление реально удаляет»), поэтому лучше делать удаление без блокирующего диалога или с легко нажимаемым подтверждением.
22. **Drag-and-drop.** Нужно HTML5 DnD (draggable, dragstart/dragover/drop). Автоматизация через браузер может не воспроизвести нативный DnD. Для надёжности стоит обработать и события pointer, а также оставить смену статуса через форму. Что делать с перетаскиванием на ту же колонку — ничего.
23. **Drag-and-drop и фильтры.** Карточки скрытые фильтром не отображаются и не перетаскиваются. Статус меняется только у перетаскиваемой задачи.
24. **Представление «по сотрудникам».** Состав не задан: вероятно, строки сотрудников с задачами, нагрузкой и прогрессом плюс группа «Без ответственного». Что именно входит в `employee-*` и `employees-view`, нужно решить так, чтобы `load-*` и `progress-*` были доступны в обоих представлениях или как минимум в сводке сотрудников. Это согласовать с QA-02 («все четыре прогресса видны»).
25. **Доступность сотрудников и вне диапазона.** Поле `capacity-*`: целое или с шагом 0,5? Допустим ли пустой ввод? SPEC: 0–168. Для значений вне диапазона или нечисловых — показать ошибку и не сохранять, вернуть прежнее значение. Способ показа ошибки не определён (где `task-error` не подходит).
26. **Где хранится доступность.** `capacities[week]` у сотрудника. Базовое `capacity` остаётся значением по умолчанию. Изменение на одной неделе не должно менять `capacity` и другие недели (QA-07). Если пользователь вводит значение, равное базовому, всё равно записывать явное значение (проще и предсказуемо).
27. **Начальная неделя и «текущая».** `current-week` — вероятно, индикатор/кнопка текущей выбранной недели (метка диапазона или возврат к DEMO_WEEK). Реальная дата 2026-10-05 не равна DEMO_WEEK, поэтому «сегодня» использовать нельзя: начальная неделя фиксирована 2026-09-28. Отсутствие явного описания функции `current-week` — неоднозначность; безопасно: элемент показывает дату выбранной недели и по клику возвращает к DEMO_WEEK.
28. **Формат даты недели.** Показывать ISO или в русском формате («28 сент. – 4 окт. 2026»), для проверок желательно сохранить ISO в тексте или атрибуте (например, `data-week`).
29. **Размеры и перенос.** Нет горизонтального скролла на 390 px, включая таблицу сотрудников, канбан с тремя колонками и форму. Для канбана на узких экранах колонки идут стопкой, а не горизонтальной прокруткой. Подтверждать измерением `scrollWidth <= clientWidth`.
30. **Ошибки формы.** При нескольких ошибках — показывать все или первую? Не указано; достаточно текста в `task-error` внутри открытой формы. Нужно подумать о `aria-live`/`role="alert"`.
31. **Модальная форма или панель.** Форма может быть модальной или встроенной. Контракт требует только, чтобы элементы существовали и были доступны. Для клавиатуры нужны фокус-ловушка и Esc, если форма модальная; метки `<label for>` обязательны.
32. **Редактирование недели задачи.** Если пользователь меняет неделю задачи на другую, задача исчезнет из текущего вида. Нужно решить, оставлять ли сообщение. SPEC допускает редактирование поля «неделя».
33. **Роли и модели.** SPEC говорит, что все роли используют Qwen3 Coder Next, а этот анализ выполнен другой моделью. Это не влияет на критерии. Влияет только формулировка про «первый полный замер»: для воспроизводимости артефактов указывать фактического исполнителя роли.
34. **Дублирование контракта.** DOMAIN-CONTRACT перечисляет «девять независимых проверок» в acceptance.test.mjs, и в файле их действительно девять (одна из них — монолитная на `monday`). Расхождений по числу нет.
35. **Не определено поведение `applyPlan` для плана, устаревшего относительно состояния** (задача удалена, статус изменён между предпросмотром и применением). Предложение: пропускать назначения для отсутствующих или уже done задач и не падать. В UI при открытом предпросмотре блокировать правки либо пересчитывать план.
36. **Предпросмотр в UI.** Содержимое `plan-preview` не задано. Предложение: таблица «задача → было → станет» и сводка нагрузки по сотрудникам после применения, плюс `unassignedHours`. Должна быть видна перегрузка (после плана — 0).

1. Дизайнер: подробное задание по UI-контракту (раздел 2.5), структуре, адаптивности и состояниям форм до начала реализации.
