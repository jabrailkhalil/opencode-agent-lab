# Анализ для дизайнера: «Поток»

Источники: docs/BRIEF.md, docs/INTERFACES.md, docs/seed-state.json; для уточнения контрактов прочитан tests/acceptance.test.mjs (не изменялся). Код не писался.

## 1. Проверка формул на seed

Формулы (неделя W, сотрудник e; задачи только с week = W и assignee = e):
- `hours` = сумма часов задач со статусом ≠ done (todo и doing — обе активные).
- `capacity` = `capacities[W]`, если ключ существует (в т.ч. 0), иначе `capacity`. Проверять через `in`/`!== undefined`, не через `||`.
- `percent` = `capacity > 0 ? Math.round(hours / capacity * 100) : null`.
- `overload` = `Math.max(0, hours - capacity)` (при capacity 0 это все активные часы).
- `totalHours` = все часы e за W, `doneHours` = часы done; `progress` = `totalHours > 0 ? Math.round(doneHours / totalHours * 100) : 0`.

Пересчёт seed (80 ч всего, 7 активных задач, 70 активных ч — сходится: 16+16+8+6+8+12+4+6+4 = 80; без done TASK-107/108 остаётся 70; TASK-109 без ответственного, 4 ч):

| Сотрудник | активные ч / доступно | percent | overload | done / всего | progress |
|---|---|---|---|---|---|
| Анна | 32 / 24 | 133 (1,333) | 8 | 0 / 32 | 0 |
| Дмитрий | 14 / 32 | 44 (43,75) | 0 | 0 / 14 | 0 |
| Мария | 8 / 24 | 33 | 0 | 6 / 14 | 43 (42,86) |
| Илья | 12 / 24 | 50 | 0 | 4 / 16 | 25 |

Часы без ответственного (4 ч) не входят ни в чью нагрузку, но входят в общие 80/70. Все значения из брифа подтверждены расчётом.

## 2. Что фиксируют приёмочные тесты

- `loadFor(...).tasks` содержит ВСЕ задачи сотрудника за неделю, включая done (тест 2: после done у Анны `tasks.length === 2`, `hours` 16, `progress` 50).
- Тест 3: все доступности недели = 0, у Дмитрия 16. Ожидается `unassignedHours === 54` (70 − 16), то есть упаковка должна реально заполнить 16 ч. Алгоритм «сначала оставить текущих исполнителей» даст 14 ч и 56 — не подходит. Нужен жадный «крупные первыми» без обязательной липкости.
- Тест 3/4: после applyPlan `overload === 0` у всех; done-задачи не меняются (deepEqual); число и ID задач прежние. В тесте 4 (seed) после применения нет ни одной задачи без ответственного (включая TASK-109).
- Тест 4: задача TASK-999 другой недели (100 ч) не участвует ни в нагрузке, ни в плане, остаётся deepEqual.
- Тест 5: capacity 0 → `percent === null`, `overload === 32`, `progress` конечно.
- Тест 6: hours −1, 0, 0.7, 169, NaN, Infinity — отклонять; 0.5 — принимать; пустое название после trim и несуществующий assignee — отклонять.
- Тест 7: `isValidState` — seed после JSON-цикла true; дубль ID false; `nextId: -1` false.
- Тест 8: `monday('2026-10-04')` (воскресенье) → `2026-09-28`.
- `proposePlan`/`applyPlan` не должны мутировать вход (тест 3 сравнивает state с клоном).

## 3. Неоднозначности и принятые решения

1. **Поле `active` в loadFor** (число или массив?) — в контракте не определено. Решение: массив активных задач (параллельно `tasks`); количество — `active.length`. `hours` — активные часы.
2. **Неизвестный сотрудник в loadFor** — бросать Error (UI вызывает только с реальными id).
3. **Percent при capacity 0 и hours 0** — `null` (по контракту при нулевой доступности); UI показывает «нет доступности», не «0%».
4. **Дробная доступность**: диапазон 0–168; шаг 0,5, как у оценки. Нечисло/вне диапазона — ошибка у поля, прежнее значение возвращается.
5. **validateTask**: `id` необязателен (новый id выдаёт UI из `nextId`, затем `nextId++`; ID после удаления не переиспользуются). Описание необязательно (пусто → `''`), trim, ≤1000. `assignee` `''`/`undefined` → `null`. Оценка — только конечное число (строки из формы UI приводит сам; пустая строка = ошибка, не 0). Шаг: `hours*2` целое. Неделя — строка `YYYY-MM-DD`, существующая дата и понедельник; **не подстраивать**, показывать ошибку.
6. **isValidState**: version 1, 4+ сотрудников с уникальными id, `capacity` и `capacities[понедельник]` в 0–168, задачи проходят правила validateTask, уникальные id формата `TASK-N`, assignee существует или null, `nextId` целое ≥ 110 и больше любого N среди задач.
7. **monday(date)**: принимает `YYYY-MM-DD` (и Date — берёт локальные компоненты), считает через `Date.UTC`; воскресенье → предыдущий понедельник; неверный ввод → Error. Перелистывание недели ±7 дней тоже в UTC.
8. **Алгоритм proposePlan**: активные задачи недели (≠ done) сортировать по часам убыв., затем по id. Кандидаты — сотрудники с остатком ≥ hours; предпочесть текущего исполнителя, иначе наибольший остаток, иначе порядок списка. Не поместилась → `assignee: null`, часы в `unassignedHours`. В `assignments` — запись на каждую активную задачу недели. Жадность не оптимальна, но тест 54 выполняется.
9. **applyPlan** (недели в сигнатуре нет): работает с клоном, меняет только задачи из плана, которые существуют и не done; assignee обязан быть сотрудником или null, иначе пропуск. Остальное не трогается.
10. **Предпросмотр (UI)**: план хранится вне state; при смене недели, правке задач/доступности он отменяется или пересчитывается (выбрать отмену — проще и безопаснее). Предпросмотр показывает «было → стало» и нераспределённые часы; применяется только `plan-apply`.
11. **Поиск/фильтр**: регистр не важен, по title+description после trim. Нагрузка, прогресс и план считаются по всем задачам недели независимо от поиска и фильтра. Опции «без ответственного» в `filter-assignee` нет (по контракту: id или пусто).
12. **`current-week`**: контракт не говорит, метка это или кнопка. Решение: кнопка-метка с текстом, содержащим ISO-дату начала недели (`2026-09-28`) и читаемый диапазон; клик возвращает на DEMO_WEEK. Реальная «сегодняшняя» неделя (2026-10-05) не используется — бриф задаёт 2026-09-28.
13. **Подтверждения**: reset-demo обязателен (бриф). Удаление — тоже с подтверждением. Подтверждение — собственное модальное окно на странице (кнопки «Подтвердить»/«Отмена», дополнительно `confirm-ok`/`confirm-cancel`), не `window.confirm`: диалог браузера автоматизация может отклонить.
14. **Хранилище**: ключ `potok-state-v1`, пишется только доменное состояние. Неделя, вид, поиск не сохраняются (старт всегда с 2026-09-28, доска). Ошибка JSON/isValidState/недоступный localStorage → seed + заметное предупреждение, без падения; битое значение перезаписывается при первом изменении.
15. **Новая задача**: неделя по умолчанию — просматриваемая, статус «Новая», ответственный «Без ответственного». Если после правки недели задача ушла из текущей недели, показать уведомление.
16. **Drag-and-drop**: HTML5 DnD между `column-*` меняет только статус; сброс в ту же колонку — без изменений. Клавиатурная альтернатива — `task-status` в форме правки.

## 4. Рекомендации по UI/архитектуре

- В dist только CSS Tabler (JS и иконок нет): модальные окна, вкладки и тосты делать собственным JS на классах Tabler/Bootstrap (`modal d-block show`, фокус-ловушка, Esc).
- Четыре карточки сотрудников (`employee-*`, `load-*`, `progress-*`, `capacity-*`) держать в постоянной панели, видимой в обоих видах; значения с подписями («Загрузка 32 / 24 ч · 133% · перегрузка +8 ч», «Прогресс 43%»). Перегрузка — красный бейдж, не только цветом.
- Рендерить только активный вид (`board` или `employees-view`), иначе `task-TASK-*` задвоятся. В виде сотрудников есть группа «Без ответственного».
- На 390 px: колонки доски в одну колонку/скролл внутри блока, не всей страницы; карточки сотрудников в одну колонку; `overflow-wrap:anywhere` для названий; проверить 768/1100/1280 без `overflow-x`. Визуально без браузера не проверено — это только требование.
- Форма: подписи `label for`, ошибка в `task-error` (`role="alert"`) внутри открытой формы, значения не сбрасываются, `novalidate` (пустое название должно ловиться прикладной валидацией). Сохранение поля доступности — на `change`/`blur`.
- Модули (результат — только index.html, styles.css, app.js, domain.js): domain.js — чистые функции без DOM; app.js — хранилище, рендер, события (можно ES-модулями внутри app.js секциями). Любое изменение — иммутабельное обновление state → сохранение → перерисовка.
- Риски: ложное использование `||` при capacity 0; мутация state в proposePlan; округление `Math.round` строго по контракту; NaN из пустых полей формы.
