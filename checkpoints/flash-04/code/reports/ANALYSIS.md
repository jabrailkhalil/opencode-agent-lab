# ANALYSIS — формулы и неоднозначности (для дизайнера и разработчика)

Проверено: docs/BRIEF.md, docs/INTERFACES.md, docs/seed-state.json, tests/acceptance.test.mjs. Код не писался.

## 1. Формулы (подтверждены расчётом по seed)

Область расчёта: задачи с `week === текущая неделя` и `assignee === employeeId`.
- capacity(сотрудник, неделя) = `employees[].capacities[week]`, если ключ есть, иначе `capacity`.
- active / hours = задачи todo|doing; hours = их сумма.
- doneHours = сумма задач done; totalHours = hours + doneHours (знаменатель прогресса).
- overload = max(0, hours − capacity).
- percent = capacity === 0 ? null : Math.round(hours / capacity * 100).
- progress = totalHours === 0 ? 0 : Math.round(doneHours / totalHours * 100).

## 3. Неоднозначности и принятые решения

1. Что в `loadFor.tasks` — только активные задачи (todo/doing): тест 2 требует `tasks.length === 2` после перевода TASK-101 в done. `active` — их количество.
2. Знаменатель прогресса «все назначенные часы» = hours + doneHours конкретного сотрудника; задачи `assignee: null` в прогресс не входят.
3. `percent` и `progress` округлять Math.round (133.33→133, 42.86→43). `percent = null` только при capacity 0; `progress = 0` при totalHours 0 — NaN/Infinity запрещены.
4. proposePlan переназначает с нуля все активные задачи недели, включая уже назначенные. Иначе тест 3 (unassignedHours 54) нерешаемем: при емкостях 0/16/0/0 в 16 ч попадает ровно одна 16-часовая задача (TASK-101 или 102), unassigned = 70 − 16 = 54. Не помещается → `assignee = null` после applyPlan.
5. Алгоритм: LPT — по убыванию часов, каждому сотруднику с наибольшей свободной ёмкостью. На seed (ёмкости 24/32/24/24, 70 ч) расклад без перегрузки и без null — тест 4 проходит. Планировщик детерминирован; tie-break по id сотрудника.
6. applyPlan меняет только assignee активных задач недели; done, другие недели, состав и суммы часов сохраняются (тесты 3, 5); исходный state не мутируется (тест 3 deepEqual).
7. monday: разбор строки по частям и Date.UTC-арифметика ((day+6)%7), форматирование через UTC — иначе сдвиг часового пояса ломает тест 9.
8. validateTask: reject для [-1, 0, 0.7, 169, NaN, Infinity], принимает 0.5 и 168; название trim 1–140 (пробелы → пусто → ошибка); null-ответственный валиден. Возврат нормализованной копии без мутации входа.
9. isValidState: `nextId < 110` трактовать буквально по брифу — требование `Number.isInteger(nextId) && nextId >= 110` (тест кидает −1; 110 = стартовое значение seed).
10. Поиск/фильтр — только видимость карточек; метрики нагрузки всегда от полного набора данных недели (бриф п.4).

## 4. Следствия для UI (дизайнеру)

- В строке каждого сотрудника нужны подписанные величины с testid: загрузка (часы), percent или «—» при null, перегрузка числом + подпись, прогресс отдельно.
- Формат percent: «133%»; при capacity 0 вместо процента — «—» или «нет доступности», но не 0%.
- Ошибки формы — внутри task-form (task-error), значения полей не сбрасывать; цвета из DESIGN-REFERENCE (перегрузка #d63939, done #2fb344).
- Кнопки edit-*/delete-* — реальные, в карточках task-TASK-1NN; drag-and-drop зоны column-todo/doing/done с той же моделью статуса, что и select в форме.
