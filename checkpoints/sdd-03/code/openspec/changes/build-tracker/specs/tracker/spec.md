## ADDED Requirements

### Requirement: Модель данных и начальное состояние
Система MUST хранить состояние вида `{version, employees, tasks, nextId}` с ровно четырьмя сотрудниками (`anna`, `dmitry`, `maria`, `ilya`). `seedState()` SHALL возвращать независимую копию данных `docs/seed-state.json` (9 задач, 80 часов всего, 7 активных задач и 70 активных часов). Все показатели MUST вычисляться из данных, а не быть захардкоженными.

#### Scenario: Начальные данные соответствуют учебному примеру
- **WHEN** приложение открывается впервые без сохранённого состояния
- **THEN** показаны 9 задач недели `2026-09-28`, из них 7 активных на 70 часов, всего 80 часов

#### Scenario: Копия seed независима
- **WHEN** вызывающий код изменяет результат `seedState()`
- **THEN** следующий вызов `seedState()` возвращает неизменённые данные

### Requirement: Создание, просмотр, редактирование и удаление задач
Пользователь SHALL иметь возможность создавать, просматривать, редактировать и удалять задачи с полями: название, описание, ответственный (сотрудник или «Без ответственного»), оценка в часах, статус, неделя. Новая задача MUST получать уникальный id вида `TASK-<nextId>`, после чего `nextId` MUST увеличиваться. Каждая карточка MUST содержать реальные кнопки изменения и удаления (`edit-<id>`, `delete-<id>`).

#### Scenario: Создание задачи
- **WHEN** пользователь нажимает «new-task», заполняет корректные значения и нажимает «task-save»
- **THEN** форма закрывается, новая карточка появляется в колонке выбранного статуса, метрики пересчитываются

#### Scenario: Редактирование задачи
- **WHEN** пользователь нажимает `edit-TASK-101`, меняет оценку и сохраняет
- **THEN** карточка `task-TASK-101` показывает новую оценку, остальные поля не меняются

#### Scenario: Удаление задачи
- **WHEN** пользователь нажимает `delete-TASK-109` и подтверждает удаление
- **THEN** карточка `task-TASK-109` исчезает из доски и из представления по сотрудникам

### Requirement: Валидация задачи
`validateTask(task, employees)` MUST возвращать нормализованную копию либо бросать `Error`, не мутируя вход. Правила: название после trim 1–140 символов; описание после trim до 1000 символов; оценка 0,5–168 с шагом 0,5; ответственный — id существующего сотрудника или `null`; статус — `todo`, `doing` или `done`; неделя — дата-понедельник в формате `YYYY-MM-DD`. Форма MUST выполнять прикладную trim-валидацию независимо от HTML `required`.

#### Scenario: Пустое название
- **WHEN** название состоит только из пробелов
- **THEN** `validateTask` бросает `Error`, а в форме отображается `task-error`

#### Scenario: Некорректная оценка
- **WHEN** оценка равна 0,3, 169 или 1,25
- **THEN** валидация отклоняет задачу

#### Scenario: Неизвестный ответственный или статус
- **WHEN** ответственный не существует среди сотрудников или статус не из `todo`/`doing`/`done`
- **THEN** валидация отклоняет задачу

#### Scenario: Неделя не понедельник
- **WHEN** неделя задана датой, не являющейся понедельником
- **THEN** валидация отклоняет задачу

#### Scenario: Нормализация
- **WHEN** название и описание содержат пробелы по краям
- **THEN** возвращённая копия содержит обрезанные значения, а исходный объект остаётся без изменений

### Requirement: Поведение формы при ошибке
При ошибке валидации форма MUST оставаться открытой, `task-error` MUST показывать понятное сообщение, а введённые пользователем значения MUST NOT сбрасываться. Все поля формы SHALL иметь подписи. `task-assignee` SHALL быть select со значениями `employee.id` и пустым значением для `null`; `task-status` SHALL быть select со значениями `todo`/`doing`/`done`.

#### Scenario: Ошибка сохраняет введённое
- **WHEN** пользователь вводит описание и оценку, оставляет название пустым и нажимает «task-save»
- **THEN** форма остаётся открытой, виден `task-error`, описание и оценка сохраняют введённые значения, состояние задач не изменено

#### Scenario: Отмена формы
- **WHEN** пользователь нажимает `task-cancel`
- **THEN** форма закрывается, данные не изменяются

### Requirement: Статусы и доска
Система MUST поддерживать статусы `todo` («Новая»), `doing` («В работе»), `done` («Готово») и отображать доску из трёх колонок `column-todo`, `column-doing`, `column-done` в контейнере `board`. Карточки SHALL переноситься между колонками drag-and-drop, статус SHALL также меняться через форму. Перенос MUST менять только статус задачи и пересчитывать метрики.

#### Scenario: Перенос карточки
- **WHEN** пользователь перетаскивает `task-TASK-106` в `column-done`
- **THEN** статус задачи становится `done`, задача перестаёт считаться активной, прогресс Ильи пересчитывается

#### Scenario: Смена статуса через форму
- **WHEN** пользователь выбирает в `task-status` значение «В работе» и сохраняет
- **THEN** карточка отображается в колонке `column-doing`

### Requirement: Представление по сотрудникам
Система SHALL предоставлять второе представление `employees-view`, переключаемое кнопками `view-board` и `view-employees` и использующее те же данные. В нём для каждого сотрудника (`employee-anna`, `employee-dmitry`, `employee-maria`, `employee-ilya`) MUST быть доступны его задачи, загрузка (`load-<id>`) и прогресс (`progress-<id>`) с подписями.

#### Scenario: Переключение представлений
- **WHEN** пользователь нажимает `view-employees`, затем `view-board`
- **THEN** сначала виден `employees-view`, затем `board`, состав и значения задач одинаковы

#### Scenario: Изменение видно в обоих представлениях
- **WHEN** задача создаётся или переназначается в одном представлении
- **THEN** изменение отражается в другом без перезагрузки

### Requirement: Поиск и фильтр по ответственному
Поле `search` SHALL фильтровать видимые карточки по подстроке в названии или описании без учёта регистра. Select `filter-assignee` SHALL оставлять только задачи выбранного сотрудника, пустое значение показывает всех. Поиск и фильтр MUST влиять только на видимый список карточек и MUST NOT менять недельные метрики загрузки и прогресса.

#### Scenario: Поиск по названию
- **WHEN** пользователь вводит в `search` фрагмент названия одной задачи
- **THEN** остаются только подходящие карточки

#### Scenario: Метрики не зависят от поиска
- **WHEN** поиск скрывает все задачи Анны
- **THEN** `load-anna` по-прежнему показывает 32 из 24 ч, 133%

#### Scenario: Фильтр по ответственному
- **WHEN** в `filter-assignee` выбран `maria`
- **THEN** видны только задачи Марии

### Requirement: Навигация по неделям
Стартовая неделя SHALL быть `2026-09-28`. Кнопки `prev-week`, `next-week` SHALL сдвигать текущую неделю на 7 дней, `current-week` SHALL возвращать к начальной неделе. `monday(date)` MUST возвращать понедельник в формате `YYYY-MM-DD` независимо от часового пояса. Задачи и недельная доступность разных недель MUST быть независимы.

#### Scenario: Следующая неделя пуста
- **WHEN** пользователь нажимает `next-week`
- **THEN** отображается неделя `2026-10-05` без задач seed, загрузка у всех 0 ч

#### Scenario: Возврат к начальной неделе
- **WHEN** пользователь переходит на другую неделю и нажимает `current-week`
- **THEN** отображается неделя `2026-09-28` и её задачи

#### Scenario: Понедельник не зависит от часового пояса
- **WHEN** `monday` вызывается с датой воскресенья `2026-10-04`
- **THEN** результат равен `2026-09-28`

### Requirement: Недельная доступность
Для каждого сотрудника поле `capacity-<id>` SHALL позволять изменить доступность на текущую неделю в диапазоне 0–168 ч. Значение MUST сохраняться при `change`/`blur` в `employees[].capacities[week]`; при отсутствии записи MUST использоваться базовое `capacity`. Недопустимое значение MUST быть отклонено без изменения состояния.

#### Scenario: Изменение доступности
- **WHEN** пользователь задаёт `capacity-anna` = 40 и покидает поле
- **THEN** загрузка Анны на текущей неделе считается от 40 ч, а на других неделях остаётся прежней

#### Scenario: Недопустимое значение
- **WHEN** в `capacity-anna` введено 169 или -1
- **THEN** значение не сохраняется и пользователь видит сообщение об ошибке

### Requirement: Метрики загрузки и прогресса
`loadFor(state, employeeId, week)` MUST возвращать `{tasks, active, hours, capacity, totalHours, doneHours, overload, percent, progress}`. Загрузка SHALL считаться по незавершённым (`todo`, `doing`) задачам; выполненные MUST NOT занимать доступность. `percent` = `Math.round(hours / capacity * 100)` и `null` при нулевой доступности; `overload` = `max(0, hours - capacity)`; `progress` = округлённый процент `doneHours / totalHours` и `0` при отсутствии назначенных часов. Результаты MUST NOT содержать `NaN` и `Infinity`.

#### Scenario: Перегрузка Анны
- **WHEN** считается `loadFor(seed, 'anna', '2026-09-28')`
- **THEN** `hours` = 32, `capacity` = 24, `percent` = 133, `overload` = 8

#### Scenario: Прогресс Марии и Ильи
- **WHEN** считается прогресс по seed
- **THEN** у Марии 43% (6 из 14 ч), у Ильи 25% (4 из 16 ч)

#### Scenario: Нулевая доступность
- **WHEN** доступность сотрудника на неделе равна 0 при наличии активных часов
- **THEN** `percent` равен `null`, `overload` равен активным часам, UI не показывает `NaN`/`Infinity`

#### Scenario: Нет назначенных часов
- **WHEN** у сотрудника нет задач на неделе
- **THEN** `progress` равен 0, `hours` равен 0

### Requirement: Предложение распределения
`proposePlan(state, week)` MUST возвращать `{assignments:[{taskId,assignee}], unassignedHours}` для активных задач выбранной недели и MUST NOT мутировать `state`. Назначения SHALL NOT превышать недельную доступность сотрудника; не поместившиеся задачи MUST получить `assignee: null` и учитываться в `unassignedHours`. `applyPlan(state, plan)` MUST возвращать новое состояние с применёнными назначениями, не изменяя выполненные задачи, задачи других недель, количество задач и общий объём часов. Интерфейс SHALL предоставлять `propose-plan`, `plan-preview`, `plan-apply`, `plan-cancel`; изменения применяются только по явному `plan-apply`.

#### Scenario: Предпросмотр не меняет план
- **WHEN** пользователь нажимает `propose-plan`
- **THEN** отображается `plan-preview`, а назначения задач и метрики остаются прежними

#### Scenario: Отмена
- **WHEN** пользователь нажимает `plan-cancel`
- **THEN** предпросмотр закрывается, состояние не изменено

#### Scenario: Применение
- **WHEN** пользователь нажимает `plan-apply`
- **THEN** активные задачи получают предложенных ответственных, и ни у одного сотрудника активные часы не превышают его доступность

#### Scenario: Задача не помещается
- **WHEN** суммарная доступность меньше суммы активных часов
- **THEN** не поместившиеся задачи остаются без ответственного, `unassignedHours` равен их сумме

#### Scenario: Инварианты применения
- **WHEN** план применён
- **THEN** выполненные задачи и задачи других недель не изменены, число задач и общий объём часов прежние, исходное состояние не мутировано

### Requirement: Сохранение состояния
Система MUST сохранять состояние в `localStorage` после каждого изменения и восстанавливать его при загрузке. `isValidState(state)` MUST принимать корректно сериализованный seed и отклонять дубли id, неправильные поля и `nextId` < 110. Повреждённые или невалидные сохранённые данные MUST NOT приводить к падению приложения: SHALL использоваться seed. `dist/domain.js` MUST NOT обращаться к DOM и `localStorage` при импорте.

#### Scenario: Сохранение после перезагрузки
- **WHEN** пользователь изменяет задачу и перезагружает страницу
- **THEN** изменение сохранено

#### Scenario: Повреждённый JSON
- **WHEN** в `localStorage` лежит невалидный JSON
- **THEN** приложение загружается с учебным примером и без ошибок

#### Scenario: Невалидная структура
- **WHEN** состояние содержит дубликаты id задач или `nextId` меньше 110
- **THEN** `isValidState` возвращает `false`

### Requirement: Восстановление учебного примера
Кнопка `reset-demo` SHALL восстанавливать seed-состояние только после явного подтверждения пользователя. Без подтверждения данные MUST NOT изменяться.

#### Scenario: Подтверждено
- **WHEN** пользователь нажимает `reset-demo` и подтверждает действие
- **THEN** состояние заменено учебным примером

#### Scenario: Отклонено
- **WHEN** пользователь нажимает `reset-demo` и отказывается
- **THEN** текущие данные остаются без изменений

### Requirement: Адаптивный и доступный интерфейс
UI MUST корректно отображаться при ширине 390, 768, 1100 и 1280 px без горизонтального переполнения; нагрузка и прогресс каждого сотрудника MUST оставаться доступными на всех ширинах. Интерфейс SHALL использовать только локальный `dist/vendor/tabler/tabler.min.css`, без внешних ресурсов. Все поля SHALL иметь подписи, основные действия SHALL быть доступны с клавиатуры. Корневой контейнер `app` MUST появляться после загрузки, и интерфейс MUST содержать `data-testid` из `docs/INTERFACES.md`.

#### Scenario: Отсутствие горизонтального прокручивания
- **WHEN** страница открыта при ширине 390 px
- **THEN** ширина содержимого не превышает ширину окна

#### Scenario: Метрики на узком экране
- **WHEN** страница открыта при ширине 390 px
- **THEN** `load-<id>` и `progress-<id>` каждого из четырёх сотрудников доступны

#### Scenario: Управление с клавиатуры
- **WHEN** пользователь переходит по элементам клавишей Tab и активирует кнопки Enter или пробелом
- **THEN** доступны создание, редактирование, удаление задач и переключение представлений

#### Scenario: Только локальные ресурсы
- **WHEN** загружается `index.html`
- **THEN** все стили и скрипты подключены с локальных путей, обращений к внешним адресам нет
