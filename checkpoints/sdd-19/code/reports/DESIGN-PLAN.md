Роль: designer. Прочитаны BRIEF, INTERFACES, DESIGN-REFERENCE, ANALYSIS и артефакты OpenSpec. Код не писался, браузер не запускался: план основан на тексте, визуальная проверка не выполнялась.

## 1. Раскладка
Токены: акцент #206bc4, текст #182433, фон #f6f7f9, границы #e6e8ec, ошибка #d63939, готово #2fb344. Только классы Tabler + `styles.css`; JS Tabler нет (в vendor только CSS).
- **Боковая панель** (`navbar-vertical`, светлая, ≥992 px, ширина 15rem): бренд «Поток», переключатели `view-board` / `view-employees` (кнопки с `aria-pressed`), внизу `reset-demo`; все кнопки целиком внутри панели, подпись `reset-demo` переносится (см. раздел 7, правило D1). Ниже 992 px — верхняя шапка с теми же элементами, без бургера: переключатели видимы всегда, `reset-demo` уходит в нижний край страницы.
- **Основная область** сверху вниз: (1) заголовок «План команды» + строка недели; (2) действия; (3) метрики недели; (4) карточки сотрудников; (5) поиск/фильтр; (6) форма или предпросмотр, если открыты; (7) `board` либо `employees-view`.
- **Строка недели**: `prev-week` «← Прошлая», подпись «Неделя 28.09–04.10.2026», `next-week` «Следующая →», `current-week` «Текущая неделя».
- **Действия**: `new-task` («Новая задача», primary) и `propose-plan` («Предложить распределение», outline) — flex-wrap, `width:auto`, `white-space:nowrap`; на <576 px — по одной на строку, на всю ширину.
- **Правило для длинных кнопок**: их не кладём в сетку `col-3` (4 колонки). Сетка колонок допустима только для коротких метрик. Кнопки живут во flex-ряду, переносятся целиком, текст не обрезается и не сжимается.
- **Метрики недели** (4 коротких плитки: «Задач», «Часов всего», «Активных часов», «Перегружено»): 2×2 до 767 px, 4 в ряд от 768 px. Считаются по всем задачам недели, поиск их не меняет.
- **Поиск/фильтр**: `search` (label «Поиск по названию и описанию»), `filter-assignee` (label «Ответственный»; пустое значение «Все», затем 4 сотрудника).

## 2. Нагрузка и прогресс
Карточка `employee-<id>` (всегда над доской, в обоих видах): имя, затем **два раздельных блока** с разными словами и цветами, без общей полосы.
- **Загрузка** (`load-<id>`, подпись «Загрузка · активные задачи»): строка «32 / 24 ч · 133%», полоса `progress-sm`, ширина ограничена 100%. Синяя ≤100%, красная >100%. При перегрузке рядом бейдж `bg-red-lt` с текстом «Перегрузка +8 ч» (число и слово, не только цвет); при ≤100% — «В пределах доступности».
- **Прогресс** (`progress-<id>`, подпись «Прогресс · выполнено»): «6 из 14 ч · 43%», зелёная полоса (`role=progressbar`, `aria-valuenow`, `aria-label`). Нет часов — «Нет назначенных часов · 0%».
- **Нет доступности** (capacity=0): вместо процента — «нет доступности», красный бейдж «Перегрузка +N ч» (если есть активные часы), полоса пустая; прогресс остаётся числом. Никаких null/NaN/Infinity в тексте.
- **Доступность**: поле `capacity-<id>`, label «Доступно, ч на неделю», `number`, min 0, max 168, step 0.5; сохранение на change/blur. Ошибка — под полем (`role=alert`, id `capacity-error-<id>`), значение откатывается, поле получает `aria-invalid`.
- Одинаковый порядок блоков у всех карточек; тексты загрузки и прогресса не сокращаются на узких экранах, а переносятся.

## 3. Форма и ошибки
Форма `task-form` — встроенная карточка (не модалка) над доской; открывается по `new-task`/`edit-*`, фокус на `task-title`, `novalidate`.
- Порядок: название, описание, ответственный, статус, оценка (ч), неделя; у каждого `label for`, у обязательных «*» и подсказка («1–140 символов», «0,5–168, шаг 0,5», «понедельник»).
- Сетка: поля «ответственный / статус / оценка / неделя» — 2×2 от 576 px, 1 колонка ниже; 4 в ряд не делаем (select с длинным текстом).
- Ошибка: `task-error` (`alert alert-danger`, `role=alert`) стоит прямо над кнопками внутри формы, текст — сообщение `validateTask` по-русски. Поле с причиной получает `is-invalid`+`aria-invalid` (определяется по тексту/полю проверки), фокус на него. Значения и открытая форма не перерисовываются; при успехе ошибка очищается.
- Кнопки: `task-save` «Сохранить», `task-cancel` «Отмена» — flex-ряд, на 390 px на всю ширину; Enter в полях отправляет форму, Esc = отмена.
- Режим правки: заголовок «Изменить TASK-101», поля предзаполнены; недельная дата — `type=date` + проверка понедельника в `validateTask`.

## 4. Пустые состояния
Блок `empty-state` (иконка не обязательна): заголовок + одна строка пояснения + действие.
- **Пустая колонка доски**: «Нет задач» (серый текст в зоне drop сохраняет высоту ≥ 6rem, чтобы можно было бросить карточку).
- **Неделя без задач**: вместо доски «На этой неделе задач нет» + кнопка «Новая задача»; карточки сотрудников остаются: 0 / доступно ч, «Нет назначенных часов · 0%».
- **Поиск/фильтр ничего не нашли**: «Ничего не найдено» + кнопка «Сбросить поиск и фильтр»; метрики и нагрузка не меняются.
- **Сотрудник без задач** (в `employees-view`): «Нет задач на этой неделе»; группа «Без ответственного» без задач — «Все задачи распределены».
- **Нет активных задач для плана**: `propose-plan` остаётся доступной, предпросмотр сообщает «Нет активных задач для распределения», `plan-apply` отключён.
- **Повреждённые данные**: `alert alert-warning` вверху с текстом «Сохранённые данные повреждены, загружен учебный пример» и кнопкой закрытия; `app` виден.

## 5. Предпросмотр плана
`plan-preview` — карточка над доской, `role=region`, `aria-labelledby`; фокус на заголовке «Предпросмотр распределения». Данные и localStorage не меняются.
- Итог: «Назначено задач: N · без ответственного: M ч» (`alert-warning`, если M>0, с пояснением «не помещается в доступность»).
- Таблица «Задача | Было | Станет | Изменение»: «Изменится» (жирно, `bg-blue-lt`) либо «Без изменений»; без изменения ответственного строки не подсвечиваем. На <768 px таблица превращается в карточки-строки (подписи через `data-label`), без горизонтальной прокрутки.
- Блок «Нагрузка после применения»: 4 строки «Анна 24 / 24 ч · 100%» (расчёт `loadFor` на копии с применённым планом, виден только в предпросмотре); основные `load-*` не трогаем.
- Кнопки `plan-apply` «Применить распределение» (primary) и `plan-cancel` «Отмена» — flex-ряд. Esc = отмена. После применения: предпросмотр закрыт, `aria-live` сообщает «Распределение применено».
- Пока предпросмотр открыт, `propose-plan` отключена; любое изменение данных (правка, drag, доступность, смена недели) закрывает предпросмотр как устаревший.

## 6. Подтверждения и доступность
- Удаление и `reset-demo`: встроенная плашка `alert` (`role=alertdialog`) рядом с источником: «Удалить TASK-109 «название»?» / «Заменить данные учебным примером?», кнопки «Удалить»/«Восстановить» (`data-testid="confirm-yes"`) и «Отмена» (`confirm-no`). Фокус на «Отмена», Esc отменяет. Нативный `confirm` не используем.
- Карточка `task-<id>`: заголовок, бейдж ответственного, «N ч», описание ≤2 строк (`line-clamp`), кнопки «Изменить»/«Удалить» с `aria-label` «Изменить TASK-101 …» (`edit-*`, `delete-*`), не иконки без подписи. `draggable`; DnD — дополнение, основной путь через форму; зона drop получает рамку #206bc4 при наведении.
- Перегрузка/ошибка не только цветом: текст + бейдж. Статус задачи — текстовый бейдж.
- Видимый фокус (`outline 2px #206bc4`, offset 2px) на всех кнопках, полях, карточках; порядок Tab = визуальный порядок. Живые области: `aria-live=polite` для уведомлений, `role=alert` для ошибок.
- Цели нажатия ≥ 36 px высоты на 390 px; `overflow-wrap:anywhere` и `min-width:0` у заголовков/описаний.

## 7. Поведение по ширинам
Ориентиры области контента (оценка): 390 → ~366, 768 → ~736, 1100 → ~812 (с боковой панелью), 1280 → ~992.

| Элемент | 390 | 768 | 1100 | 1280 |
|---|---|---|---|---|
| Навигация | верхняя шапка, виды в 2 кнопки | то же | боковая 15rem | боковая 15rem |
| Действия | колонкой, во всю ширину | в строку, перенос | в строку | в строку |
| Метрики | 2×2 | 4 в ряд | 4 в ряд | 4 в ряд |
| Карточки сотрудников | 1 колонка | 2×2 | 2×2 | 2×2 (не 4 в ряд) |
| Доска | 3 колонки стопкой | стопкой | 3 колонки (~260 px) | 3 колонки (~320 px) |
| Форма | 1 колонка | 2×2 | 2×2 | 2×2 |
| Предпросмотр | карточки-строки | таблица | таблица | таблица |

- Нагрузка и прогресс — внутри карточки сотрудника на всех ширинах, не скрываются и не сворачиваются.
- Колонки доски: один ряд из 3 колонок только когда ≥992 px (есть место ≥ 240 px на колонку); в `employees-view` группы всегда стопкой.
- Никакого `overflow-x`: проверяем `scrollWidth ≤ clientWidth` на `document.documentElement` для четырёх ширин. Этого недостаточно: при `overflow-x:hidden` на `html, body` и при дефекте D1 (кнопки выступают на 16.24 px, документ при этом 1280) проверка проходит. Поэтому добавлена геометрическая проверка боковой панели ниже.

### Боковая панель: правило и проверка (дефект D1)
Основание: `BROWSER-EVIDENCE.txt` (sdd-09, 1280×900: панель right=240, `main` с x=240, кнопки left=16, right=256.24 — выступ 16.24 px) и `QA-RESULTS.md` D1. Для 1100 наблюдений нет; требование распространяется на него по тому же правилу.
- **Правило**: при ≥992 px (в т.ч. 1100 и 1280) каждая кнопка и подпись боковой панели целиком внутри панели с учётом внутренних отступов 16 px: `left ≥ 16`, `right ≤ 224`. Внутренний блок панели считает ширину вместе с отступами (`box-sizing:border-box`), а не `100% + padding`. Длинная подпись «Восстановить учебный пример» переносится на вторую строку (`white-space:normal`; правило для `.side .btn` не должно её перебивать), кнопка растёт по высоте, не по ширине.
- **Основная область не перекрывается**: `right` любого элемента панели ≤ `left` у `main` (240); `overflow-x:hidden` не используется для скрытия выступа.
- **Проверка (браузер, 1100×900 и 1280×900, затем 992)**: `getBoundingClientRect()` у `aside.side`, `main#main`, `view-board`, `view-employees`, `reset-demo`. Условия: `right` каждой кнопки ≤ 224 и ≤ `aside.right` (240); `aside.right ≤ main.left`; высота `reset-demo` ≥ высоты одной строки (перенос допустим); `scrollWidth ≤ clientWidth` как дополнительная. Результат — числа в протоколе и скриншот-артефакт; без браузера статус «не проверено».
- **Не регресс на узком экране**: на 390 и 768 панель не фиксирована, документ без переполнения (подтверждено для 390 в протоколе).
