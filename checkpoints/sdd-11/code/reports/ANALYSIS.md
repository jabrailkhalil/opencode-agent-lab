## Ключевые решения
- **Нагрузка против прогресса**: нагрузка = todo+doing / доступность; прогресс = done / все часы недели. Независимы друг от друга, от поиска/фильтра; перенос задачи в done снижает нагрузку и повышает прогресс (TASK-101 → done: Анна 16 ч, прогресс 50%).
- **Нулевая доступность**: percent=null (не Infinity), overload = активные часы, прогресс остаётся числом. В UI — текст «нет доступности». Риск реализации: `capacities[week] || capacity` потеряет 0 — в design указана проверка по наличию ключа.
- **План 70 ч при доступности 16**: по тесту (Дмитрий 16, остальные 0) unassignedHours должно быть ровно 54. Зафиксировано в spec; жадный алгоритм «крупные задачи первыми, сотруднику с наибольшим остатком» даёт 16 ч (задача TASK-101 на 16 ч) — разбор вручную, не запуск.
- **Seed-план**: все 7 активных задач, включая TASK-109 без ответственного, должны получить ответственного без перегрузки (тест 4); ручная прогонка жадного алгоритма это подтверждает.
- **Форма**: прикладная trim-валидация, `novalidate`, ошибка в task-error, значения не сбрасываются; hours шаг 0,5; неделя — понедельник.
- **Сохранение**: try/catch на чтение/запись, isValidState (дубли id, nextId<110, ссылки), fallback на seed с уведомлением, reset-demo только после подтверждения.

## Допущения и риски
- «Доступность 16» понята как 16 ч у единственного доступного сотрудника (по тесту).
- Жадный алгоритм не оптимален в общем случае; приемлемо, зафиксировано в design.
- Float с шагом 0,5 — сравнения аккуратно.
- Визуальная/браузерная проверка не выполнялась и не заявляется; по UI-требованиям (390–1280 px, клавиатура) нужна проверка тестировщиком в браузере.
