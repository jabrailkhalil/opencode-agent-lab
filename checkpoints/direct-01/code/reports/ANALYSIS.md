# Анализ для дизайнера: «Поток» (роль analyst)

Источники: docs/BRIEF.md, docs/INTERFACES.md, docs/seed-state.json. Дополнительно прочитаны tests/acceptance.test.mjs и docs/DESIGN-REFERENCE.md, чтобы проверить формулы. Файлы не менялись, код не писался, ничего не запускалось. Числа ниже посчитаны вручную по seed.

## 1. Формулы

Для сотрудника E и недели W берутся задачи, у которых `assignee === E` и `week === W`.

| Величина | Формула |
|---|---|
| `tasks` | все такие задачи, включая выполненные |
| `active` | задачи со статусом todo/doing |
| `hours` | сумма часов активных задач |
| `capacity` | `capacities[W]`, если ключ есть (проверять через hasOwn или `!== undefined`, 0 — валидное значение), иначе `capacity` |
| `overload` | `max(0, hours − capacity)` |
| `percent` | `capacity > 0 ? Math.round(hours / capacity * 100) : null` |
| `totalHours` | сумма часов всех задач сотрудника за неделю |
| `doneHours` | сумма часов задач со статусом done |
| `progress` | `totalHours > 0 ? Math.round(doneHours / totalHours * 100) : 0` |

Проверка на seed (неделя 2026-09-28):

| Сотрудник | Активные / доступно | Загрузка | Перегрузка | Выполнено / всего | Прогресс |
|---|---|---|---|---|---|
| Анна | 32 / 24 | 133% | +8 ч | 0 / 32 | 0% |
| Дмитрий | 14 / 32 | 44% (43,75) | 0 | 0 / 14 | 0% |
| Мария | 8 / 24 | 33% | 0 | 6 / 14 | 43% (42,86) |
| Илья | 12 / 24 | 50% | 0 | 4 / 16 | 25% |

- Итоги по неделе: 9 задач и 80 ч всего. Активных 7 задач и 70 ч (66 ч назначены и 4 ч TASK-109 без ответственного). Выполнено 10 ч (4 + 6). Суммарная доступность 104 ч.
- Брифу всё соответствует: Анна 32/24, 133%, +8; Мария 43%; Илья 25%.
- Сверка с тестами:
  - Тест 2: после перевода TASK-101 в done у Анны `hours`=16, `overload`=0, `progress`=16/32=50, `tasks.length`=2.
  - Тест 5: при нулевой доступности `percent`=null, `overload`=32, `progress` конечен.
- Формулы в брифе и тестах непротиворечивы.

## 2. Неоднозначности и решения

### Домен (domain.js)

1. **Тип `active`.** В интерфейсе не указан. Решение: `active` — число активных задач (для подписи «2 задачи»), `tasks` — массив. Тестами не проверяется.
2. **Нулевая доступность и 0 часов.** `percent`=null, `overload`=0. В UI показывать «—» и подпись «нет доступности», не «0%».
3. **Прогресс без задач.** `progress`=0 по контракту. В UI при `totalHours`=0 рядом добавить «нет задач», иначе 0% выглядит как «ничего не сделано».
4. **Неизвестный сотрудник в `loadFor`.** Решение: бросать Error. Состояние перед этим проходит `isValidState`.
5. **`loadFor` не нормализует неделю.** Решение: сравнение строгое, UI передаёт только понедельники. Фильтр и поиск в `loadFor` не участвуют (требование п. 4 брифа).
6. **Правила `validateTask`:**
   - Название: trim, 1–140 символов.
   - Описание: trim, ≤1000. `undefined` или `null` превращается в `''`.
   - Часы: `typeof number`, конечное, 0,5…168, кратное 0,5 (`h*2` целое). Строки из формы приводить к числу в app.js. Пустая строка, NaN и Infinity отклоняются.
   - Статус: только todo/doing/done.
   - Ответственный: `''` и `null` дают `null`, иначе id существующего сотрудника.
   - Неделя: формат YYYY-MM-DD, реальная дата (30 февраля отклоняется), день недели — понедельник. Не-понедельник отклоняется, а не «подтягивается» автоматически. `monday()` нужен только для вычислений и навигации.
   - Остальные поля (`id`) сохраняются. Вход не мутируется, возвращается копия.
   - Текст ошибки на русском, по одной причине, чтобы показать в `task-error`.
7. **`monday(date)` и навигация.** Только UTC-арифметика по частям строки (Date.UTC, getUTCDay), без локальных `new Date('YYYY-MM-DD')` с локальными геттерами. Воскресенье относится к предыдущему понедельнику (10-04 → 09-28). Недели ±7 дней считаются так же.
8. **`isValidState`:**
   - Проверки: version===1; сотрудники с уникальными id и непустыми строками; capacity в 0–168; ключи `capacities` — понедельники, значения 0–168.
   - Задачи проходят те же правила, что и `validateTask`, но без throw. Дубли id запрещены. Ответственный должен существовать или быть null.
   - `nextId` — целое ≥110. Дополнительно решение: `nextId` > максимального числового суффикса TASK-N, иначе новый id может дублироваться. Это строже брифа, но seed и штатная работа приложения ему удовлетворяют.
   - Тест 4 помещает TASK-999 вручную, но `isValidState` на нём не вызывает.
   - Любой не-объект, null или массив даёт false, без исключений.

### Распределение (proposePlan / applyPlan)

9. **Область.** Только активные задачи недели W, включая сейчас назначенные. Выполненные и задачи других недель не трогаются. Поиск и фильтр UI на план не влияют, берутся все задачи недели.
10. **Алгоритм: «с нуля», крупные задачи первыми.**
    - Сортировка по часам по убыванию, затем по id.
    - Каждая задача идёт сотруднику с наибольшим остатком доступности (при равенстве — по порядку в списке), если задача помещается. Иначе `assignee: null`.
    - Остаток считается от полной доступности недели, потому что done её не занимает.
    - Проверено вручную на seed: 101→Дмитрий, 102→Анна, 106→Мария, 103→Илья, 105→Дмитрий, 104→Илья, 109→Мария. Все назначены, перегрузок нет (тест 4).
    - **Тест 3:** доступно только у Дмитрия, 16 ч, он берёт TASK-101 (16 ч) ровно. `unassignedHours`=70−16=54.
11. **Нельзя «сохранять текущего ответственного, если помещается».** Этот вариант даёт для теста 3 Дмитрию 8+6=14 ч и `unassignedHours`=56, а тест требует 54. Дизайнеру не обещать «минимум перестановок».
12. **Ограничение жадного подхода.** Он не гарантирует оптимума. Пример: доступно 16 ч, задачи 10, 8, 8 — размещена только 10, хотя 8+8 помещается. Для приёмки достаточно, в UI не обещать «оптимальное».
13. **Состав `assignments`.** Для каждой активной задачи недели одна запись, включая `assignee: null` для не поместившихся (в том числе уже неназначенных). `unassignedHours` — сумма часов записей с null. Не поместившаяся задача, которая была у Анны, после apply становится без ответственного: иначе у недоступного сотрудника останется перегрузка (тест 3).
14. **`applyPlan`.** Возвращает глубокую копию, исходное состояние не мутируется (тест 3 сравнивает до и после). Применяются только записи с известным id, не-done задачи и существующий assignee или null. Порядок задач, их количество и сумма часов сохраняются. Меняется только `assignee`.

### UI

15. **Предпросмотр.** `plan-preview` показывает:
    - таблицу «задача: было → стало» с признаком «без ответственного»;
    - итоговую нагрузку по сотрудникам после применения;
    - `unassignedHours`.

    Если изменений нет, показывается «Изменений нет». Кнопки `plan-apply` и `plan-cancel` находятся внутри предпросмотра. Данные не меняются, пока не нажато apply. Предпросмотр закрывается при смене недели, любом изменении данных и при reset: иначе план устареет.
16. **Расположение показателей.** Каждый testid уникален. Постоянная панель «Команда» над обоими представлениями содержит `employee-*`, `load-*`, `progress-*`, `capacity-*`. Так показатели не исчезают при переключении и на 390 px (карточки в колонку). `employees-view` показывает только задачи, сгруппированные по сотрудникам и «Без ответственного», с другими testid (например `group-anna`). Пустые группы показываются с «нет задач».
17. **Тексты `load-*` и `progress-*`.**
    - Загрузка: «32 / 24 ч · 133%», при перегрузке «+8 ч перегрузка».
    - Прогресс: «Выполнено 6 из 14 ч · 43%».
    - В `load-*` нет процента прогресса, в `progress-*` нет процента загрузки (чтобы регулярка не поймала чужое число).
    - Полоса загрузки визуально ограничена 100%, число и подпись не ограничены.
    - Перегрузка передаётся числом и текстом, не только цветом.
18. **`current-week`.** Подписанный элемент недели: текст содержит ISO-дату понедельника и диапазон («2026-09-28 · 28.09–04.10.2026»), плюс `data-week`. Начальная неделя — всегда DEMO_WEEK, а не сегодняшняя дата. Неделя, представление и поиск в localStorage не пишутся.
19. **Новая неделя без задач.** Пустое состояние со ссылкой на создание. Доступность берётся из базовой `capacity`, пока для недели не задана своя. Запись `capacity-*` пишет только `capacities[W]`, другие недели не затрагиваются.
20. **Поле доступности.** `input type=number` min 0, max 168, step 0.5, сохранение на change/blur. Решение: допускается шаг 0,5, как у часов. Пустое значение, NaN или вне диапазона дают ошибку рядом с полем, прежнее значение восстанавливается, в состояние ничего не пишется.
21. **Форма.** Одна форма создания и редактирования, в модальном окне, `task-form` — реальный `<form>` с `novalidate`, чтобы работала прикладная trim-валидация. Все `label for`, `task-error` с `role="alert"` внутри формы. Значения при ошибке не сбрасываются, форма не закрывается. Esc и `task-cancel` закрывают без сохранения. Фокус возвращается на кнопку-источник. Новая задача по умолчанию получает просматриваемую неделю и статус todo. Id — `TASK-${nextId}`, затем nextId++. Если при редактировании неделя изменена на другую, задача исчезает из текущего вида. Показать короткое уведомление «Задача перенесена на неделю …».
22. **Подтверждения.** Для `reset-demo` (требование брифа) и удаления задачи — модальный диалог внутри страницы (`role="dialog"`, кнопки «Подтвердить»/«Отмена»). Рекомендуются дополнительные testid `confirm-ok` и `confirm-cancel`. Решение удалять с подтверждением принято из-за необратимости, но это риск для автоматического сценария (по INTERFACES подтверждения допустимы). Нативный `confirm()` не использовать.
23. **Drag-and-drop.** Перетаскивание карточки в `column-*` меняет только статус. Падение в ту же колонку ничего не делает. Нагрузка и прогресс пересчитываются, состояние сохраняется. Для клавиатуры равноценная замена — статус в форме редактирования (в ТЗ уже есть). Порядок карточек в колонке совпадает с порядком в `tasks`.
24. **Поиск и фильтр.** Без учёта регистра, по trim-подстроке в названии и описании. Работают только по задачам просматриваемой недели, одинаково в обоих представлениях. Фильтр: пустое значение — все, иначе id сотрудника. Опция «Без ответственного» в фильтре в контракт не входит, добавлять необязательно. Если добавить, значение должно быть вне id сотрудников (например `none`), а пустое значение остаётся «все». Метрики недели, `load-*` и `progress-*` от поиска не зависят. Отдельное пустое состояние «Ничего не найдено».
25. **localStorage.** Ключ `potok.state.v1` хранит только состояние домена. Запись после каждого изменения. При чтении ошибка парсинга, `isValidState`=false или недоступный storage — не падать: использовать `seedState()`, показать заметное предупреждение «Данные повреждены, загружен учебный пример». Повреждённое значение не удалять до первого изменения пользователем. При ошибке записи (quota, private mode) приложение работает в памяти и показывает предупреждение. `reset-demo` после подтверждения заменяет состояние копией seed и пишет его.
26. **Недельные метрики.** Над командой: задач, часов, активных задач, активных часов, без ответственного, выполнено часов. Считаются по задачам просматриваемой недели без поиска. На seed: 9 / 80 / 7 / 70 / 4 / 10. Рекомендуются необязательные testid `metric-*`. В контракте их нет, тесты на них опираться не должны.
27. **Адаптивность и Tabler.** Использовать локальный `dist/vendor/tabler/tabler.min.css`, без внешних ресурсов. На 390 px доска становится вертикальным списком колонок (или горизонтальный скролл только внутри блока колонок). Обязательное условие — отсутствие переполнения всей страницы: `scrollWidth <= innerWidth` на 390/768/1100/1280. Длинные названия переносить (`overflow-wrap:anywhere`). Цвета из DESIGN-REFERENCE. Нужны видимый focus-ring и порядок Tab от шапки к форме. Визуальная проверка без браузера не заявляется.

## 3. Остаточные риски

- Строгое правило `nextId > max id`: если скрытая проверка подаст состояние с большим числовым id и `nextId`=110, оно будет отклонено. По бриф+тестам этого не требуется. Если нужно строго по тексту интерфейса, оставить только `nextId` ≥110 целое.
- Модальное подтверждение удаления может помешать сценарию, который ожидает мгновенного удаления. Допустимость подтверждений оговорена в INTERFACES, но кнопки подтверждения без testid контроллер найдёт только по тексту (поэтому рекомендованы `confirm-ok`/`confirm-cancel`).
- Формат текста `load-*`/`progress-*` и `current-week` в контракте не зафиксирован. Решения п. 17–18 сделаны так, чтобы подходили и поиск по числу, и по ISO-дате.
- Жадное распределение не оптимально для произвольных данных (п. 12), на seed и в тестах результат корректен.
- Всё выше проверено только чтением и ручным расчётом. Сам код и тесты не запускались.
