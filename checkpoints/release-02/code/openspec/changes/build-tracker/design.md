## Context

Статическое приложение без сборки: `dist/index.html`, `styles.css`, `app.js` (UI), `domain.js` (чистая логика, ES-модуль, без DOM). Стили — локальный `dist/vendor/tabler/tabler.min.css` (не менять). Контракт — `docs/INTERFACES.md`, данные — `docs/seed-state.json`.

## Decisions

- **Разделение**: `domain.js` не знает про DOM и localStorage; всё состояние иммутабельно (функции возвращают копии). `app.js` держит состояние, рендерит и сохраняет.
- **Состояние UI** (неделя, представление, поиск, фильтр, открытая форма/план) не хранится в данных localStorage, кроме самого состояния задач/доступности. Ключ: `potok.state.v1`.
- **Недели**: даты — строки YYYY-MM-DD, арифметика через `Date.UTC`, не локальное время. Неделя задачи — ключ фильтрации; `capacities[week]` — переопределение базовой `capacity`; проверка через `Object.hasOwn`/`in`, чтобы 0 не терялся (не `||`).
- **Загрузка**: активные = todo|doing. `percent = capacity>0 ? Math.round(hours/capacity*100) : null`. `progress = totalHours>0 ? Math.round(done/total*100) : 0`. Для UI: percent=null → «нет доступности» (перегрузка показывается в часах).
- **Поиск/фильтр** применяются только при построении списка карточек; `loadFor` всегда получает полное состояние.
- **Распределение** (жадное, детерминированное): активные задачи недели сортируются по часам убыв. (ничья — по id); остаток доступности каждого сотрудника = capacity недели; задача кладётся тому, у кого остаток ≥ hours и он максимален (ничья — порядок employees). Если подходящего нет — assignee=null, часы в `unassignedHours`. Приоритет «сохранить текущего ответственного, если помещается» не вводится (упрощение, зафиксировано). Обоснование: гарантирует ограничение; на проверочном случае (доступно только 16 ч) крупнейшая задача 16 ч заполняет остаток полностью, итог unassignedHours=54, на seed все 7 задач размещаются без перегрузки (проверено расчётом вручную, код не запускался).
- **Предпросмотр**: `proposePlan` вызывается над текущим состоянием, результат хранится только в памяти UI; `plan-apply` вызывает `applyPlan` и сохраняет, `plan-cancel` отбрасывает.
- **Форма**: один компонент для создания/правки; значения читаются из DOM, проверяются `validateTask`; при Error — текст в `task-error` (role=alert), форма и значения не перерисовываются. Атрибут `novalidate`, чтобы работала прикладная проверка.
- **Хранение**: `JSON.parse` в try/catch → `isValidState` → иначе seed + уведомление. Запись в try/catch (квота). `isValidState` проверяет типы, уникальность id (задач и сотрудников), assignee ∈ employees|null, статус, понедельник, hours-шаг, nextId ≥ 110 и больше числовых суффиксов id.
- **Drag-and-drop**: HTML5 DnD на карточках и колонках; альтернатива — смена статуса в форме (клавиатура).
- **Подтверждения** (удаление, reset-demo): встроенная плашка `role=alertdialog` с кнопками `confirm-yes`/`confirm-no`, фокус на «Отмена», Esc отменяет; нативный `confirm` не используется.
- **UI**: подробности — `reports/DESIGN-PLAN.md`; решения ниже.

## UI Design

- **Раскладка**: светлая боковая панель (≥992 px: бренд, виды, `reset-demo`); ниже — верхняя шапка без бургера. Основная область: заголовок «План команды» и неделя → действия → метрики недели → карточки сотрудников → поиск/фильтр → форма/предпросмотр → `board`/`employees-view`.
- **Кнопки**: длинные («Предложить распределение», «Новая задача») — во flex-ряду с переносом, `nowrap`; на <576 px на всю ширину. Не размещать в четырёх колонках рядом с боковой панелью; колоночная сетка — только для коротких метрик.
- **Нагрузка и прогресс** — два раздельных блока карточки сотрудника со своими подписями («Загрузка · активные», «Прогресс · выполнено») и полосами: загрузка синяя/красная при >100% (полоса ≤100%, число и бейдж «Перегрузка +N ч»), прогресс зелёный с часами. При capacity=0 — «нет доступности», прогресс остаётся числом.
- **Форма**: встроенная карточка, не модалка; `task-error` над кнопками, `is-invalid`/`aria-invalid` на поле причины, фокус на него; значения не перерисовываются. Поля ответственный/статус/оценка/неделя — 2×2 от 576 px.
- **Предпросмотр**: карточка с итогом, таблицей «Было → Станет» (на <768 px — карточки-строки) и блоком «Нагрузка после применения» (расчёт на копии); основные `load-*` не меняются; устаревает при любом изменении данных.
- **Пустые состояния**: `empty-state` для пустой колонки, недели без задач, пустого поиска (кнопка сброса), сотрудника без задач, плана без активных задач; уведомление о повреждённых данных — `alert-warning`.
- **Ширины**: карточки сотрудников 1 колонка (390) / 2×2 (≥576, без 4 в ряд); метрики 2×2 → 4 в ряд от 768; доска стопкой <992, 3 колонки ≥992; нагрузка и прогресс не скрываются ни на одной ширине.
- **Дополнительные testid**: `confirm-yes`, `confirm-no`, `empty-state`, `capacity-error-<id>`.

## Risks / Trade-offs

- Жадный алгоритм не всегда находит максимальную упаковку (задача NP-трудная); для учебного объёма приемлемо.
- Дробные часы: сравнения с остатком делать в десятых/шагах 0,5, чтобы избежать ошибок float.
- В отсутствие браузера в данном прогоне визуальная проверка не выполнялась.

## Open Questions

- «Доступность 16» трактуется как суммарная доступность команды 16 ч (один сотрудник — 16, остальные 0); именно так построен приёмочный тест (Дмитрий 16).
